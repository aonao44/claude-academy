シナリオ1の解剖 ― カスタマーサポート解決エージェント

CCAR-F 公式シナリオ1を MCP 抜きで実装した labs/scenario1-no-mcp/ の中身。① 何がどこにあるか ② 事故が起きる瞬間 ③ MCP を足すと何が変わるか

1何がどこにあるか

主張：全部が1つのプロセスの中にある。外に出るのは DEFS（説明書）だけ。

2事故が起きる瞬間

主張：依頼主は田中花子（C-2044・スニーカー・9,800円）。本人確認を飛ばすと田中太郎（C-8831・12,800円）に着地する。

3MCP を足すと何が変わるか

主張：変わるのは「ツールがどのプロセスに居るか」だけ。ループも stop_reason も description の重要性も、何も変わらない。

4コード上で具体的に何が変わるか

観点MCPなし版（いま）MCP 版ドメイン
ツールの定義場所tools.py の DEFS をハードコードサーバーに問い合わせて取得（tools/list）2（18%）
ツールの実行IMPL[name](**input) ＝ 関数呼び出しtools/call を JSON-RPC で送る2（18%）
エラーの返し方{"error": ...} を自分で詰めるisError フラグ（MCP の仕様）2（18%）
設定なし.mcp.json（プロジェクト/ユーザースコープ、環境変数展開）3（20%）
起動python agent.pyサーバーを子プロセスとして起動（stdio）—
再利用この agent.py 専用Claude Code からも使える・複数サーバー同時利用2・3
ガードの置き場所クライアント（agent.py）の ifクライアント側 or サーバー側の選択が発生1・2・5
リソース（読み取り専用データ）概念なしResources（カタログ的データ）と Tools（行為）を使い分ける2（18%）

範囲の注意：MCP の設定（スコープ・環境変数展開・複数サーバー同時利用）と設計（Resources と Tools の使い分け・description の質・構造化エラー）は In-Scope。一方 MCP サーバーのデプロイ・ホスティング（インフラ、ネットワーク、コンテナ）は §17 で明示的に範囲外。自作して繋ぐところまでがやる範囲。
