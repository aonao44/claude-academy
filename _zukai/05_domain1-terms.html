00まず全体の構造 ─ 何が何の中に入っているか

固定語はバラバラの用語ではなく、1つの入れ子（ネスト）のどこかにある「キー」。先にこの木を頭に入れると、以降の表が全部この木の一部として読める。

リクエスト（自分 → Claude）… client.messages.create(...) に渡すもの ├─ model, max_tokens, system ├─ tools ［配列：説明書］ │ └─ { name, description, input_schema } ← 毎回同じ。実行結果は入らない └─ messages ［配列：会話の履歴］ ← 毎周増える ├─ { role: "user", content: "田中です…" } ← content は文字列でもよい ├─ { role: "assistant", content: ［ブロック, ブロック］ } ← ② をそのまま積む └─ { role: "user", content: ［ブロック］ } └─ { type: "tool_result", tool_use_id, content, is_error } レスポンス（Claude → 自分）… create() の戻り値 res ├─ id, type, role: "assistant", model, usage ├─ stop_reason ← 単一の値（6つの候補のうち1つ） └─ content ［配列：ブロック］ ← 複数入る ├─ { type: "text", text: "お調べします" } └─ { type: "tool_use", id, name: "lookup_order", input: {…} }
段名前中身コードでの触り方
1段目messages会話の履歴（メッセージの配列）messages.append(...)
2段目1通のメッセージrole（誰の発言か）＋ content（中身）{"role": …, "content": …}
3段目content ブロック中身の部品。type で種類が決まる（text / tool_use / tool_result）for b in res.content: → b.type

要点。レスポンスの content と、messages の中の content は同じ部品（ブロック）でできている。だから返ってきた res.content を、そのまま messages に積み直せる。

01ループ制御 ─ stop_reason

ドメイン1で最も出る。ループの終わり方を決めるのは stop_reason であって、本文テキストではない。

値意味コードの動作
"tool_use"ツールを呼んでほしい実行して tool_result を返し、ループを継続
"end_turn"回答が完成したループを抜ける
"max_tokens"max_tokens に達して途中で切れたツールは実行しない。上限を上げて再試行
"stop_sequence"指定した停止文字列に当たった用途次第
"pause_turn"サーバー側ツールの内部ループが上限（既定10回）に達したそのまま再送すると続きから再開。「続けて」を足さない
"refusal"安全上の理由で拒否したツールを実行しない。stop_details.category に分類

正ループ終了の判定

if res.stop_reason != "tool_use":
    break

状態を示す値で判定している。

誤本文テキストで判定

if "完了しました" in res.content[0].text:
    break

言い回しは確率的に変わる。選択肢として出たら誤り。

02リクエストの固定パラメータ

パラメータ必須中身
model必須モデル ID の文字列（値も Anthropic が決めている）
max_tokens必須1応答の出力上限。超えると stop_reason: "max_tokens"
messages必須会話履歴の配列。role は "user" / "assistant"
system任意システムプロンプト。messages の中ではなくトップレベル
tools任意ツール定義の配列
tool_choice任意ツールの使わせ方（→ 05）
stop_sequences任意これが出たら止める文字列

ステートレス。API は前回のやりとりを覚えていない。毎回 messages に履歴を全部載せて送る。だから周回ごとに入力トークンが増える（コンテキスト管理が別ドメインで問われる理由）。

04ツール定義（自作ツール）

{
  "name": "get_customer",
  "description": "顧客を本人確認する。email を渡すと一意に確定できる。",
  "input_schema": {
    "type": "object",
    "properties": { "email": {"type": "string"} },
    "required": ["email"]
  }
}
キー固定/自由ポイント
nameキーは固定・値は自分tool_use.name としてそのまま返ってくる
descriptionキーは固定・値は自分ツール選択の主要な機構。「何をするか」より「いつ呼ぶか」を書く
input_schemaキーは固定・中身は JSON Schematype / properties / required / enum
strict固定（任意）true で引数がスキーマに必ず適合する

選択の精度を上げる順序。①description に呼ぶ条件を書く → ②引数を減らす・enum で狭める → ③そもそも危ない引数を消す。これでも確率は 100% にならないので、金銭や削除が絡むならコード側で止める（→ 07）。

05tool_choice

値挙動使いどころ
{"type": "auto"}使うかどうかも Claude が決める（既定）通常のエージェント
{"type": "any"}必ず1つ以上使わせる必ず構造化して返させたいとき
{"type": "tool", "name": …}指定したツールを使わせる用途が1つに決まっているとき
{"type": "none"}使わせない要約だけさせたいとき

"disable_parallel_tool_use": true を添えると、1応答あたり1件までに制限できる。既定では1応答に複数の tool_use が入りうる。

06ツールの3分類

分類定義するのは実行するのは例
user-defined tools
（自作ツール）		自分自分のコードget_customer process_refund
Anthropic-defined toolsAnthropic自分のコードbash text_editor memory computer
server toolsAnthropicAnthropic のサーバーweb_search web_fetch code_execution

上2つをまとめて client tools（自分の環境で実行するツール）と呼ぶ。「実行するのは誰か」で分かれる点が問われる。

Anthropic 定義ツールの宣言 ─ type と name だけ

自作ツール

{"name": "get_customer",
 "description": "...",
 "input_schema": {...}}

引数の形は自分が教える。

Anthropic 定義ツール

{"type": "bash_20250124",
 "name": "bash"}

{"type": "text_editor_20250728",
 "name": "str_replace_based_edit_tool"}

input_schema を書かない。引数の形はモデルに組み込み済み。

  • type の日付は組み込みスキーマのバージョン。bash_20250124 は「2025-01-24 版の bash ツール仕様」。仕様が更新されると新しい日付の型が増える。
  • Claude が返す input は決まった形（bash なら {"command": "…"} か {"restart": true}）。
  • 同じ名前で自作しても別物。{"name": "bash", "input_schema": …} と書けば、ただの自作ツールになり組み込みの挙動は付かない。
  • 実行するのは自分のコード。Claude はコマンド文字列を返すだけなので、隔離環境・許可リスト・タイムアウトは自分の責任。

server tools は実行も結果もサーバー側。tools に入れて有効にするだけでよく、tool_result を返す必要がない。結果は最初からレスポンスに入っている。内部ループが上限に達すると stop_reason: "pause_turn" になる。

07往復の規則と落とし穴

規則理由
tool_result は role: "user" のメッセージで返す"tool" というロールは存在しない
tool_use_id に tool_use.id をそのまま入れるどの依頼への答えかを対応付けるため
並列の tool_use は、全部の結果を1つの user メッセージにまとめる分割して送ると、Claude が並列呼び出しをしなくなる
失敗したツールも省略せず is_error: true で返す返さないと対応関係が崩れる。Claude は誤りを認識して別の手を試せる
履歴には res.content を丸ごと積むテキストだけ抜くと tool_use が消え、次の tool_result が対応先を失う
content は文字列dict は JSON 文字列にしてから入れる

ドメイン1の中心命題。プロンプトや Few-shot は確率的にしか効かない。金銭・削除・認可のように誤りが取り返しのつかない処理は、コード側の前提条件（programmatic enforcement）で決定論的に止める。公式の表現は “deterministic guarantees that prompt-based approaches cannot”。

確率的効くが 0 にはならない

  • システムプロンプトで強く指示する
  • Few-shot で正しい順序を見せる
  • description を改善する

決定論的実行そのものを止める

  • ツール実行前の条件チェック（前提条件）
  • hooks（PreToolUse で拒否）
  • ツール自体を渡さない・引数を消す

用語意味問われ方

10頻出のひっかけ

ループの終了は、Claude の返答に「完了」と書かれているかで判定する？

誤り。stop_reason で判定する。文面は確率的に変わる。

tool_result は role: "tool" で返す？

誤り。role: "user" のメッセージに tool_result ブロックとして入れる。

並列で3件呼ばれたら、結果を3通のメッセージに分けて送る？

誤り。1通の user メッセージに3つの tool_result を入れる。分けると並列呼び出しをしなくなる。

ツールが失敗したら、その結果は送らずに次へ進む？

誤り。is_error: true を付けて必ず返す。返さないと tool_use と対応が取れない。

本人確認を必ず先に行わせたい。最も効果的なのはシステムプロンプトでの指示？

誤り。プロンプトは確率的。実行前にコードで条件を検査してブロックする（programmatic enforcement）が正解。公式サンプル問題1の論点。

Claude がツールを呼ぶので、DB の更新は Claude が行っている？

誤り。Claude は「このツールをこの引数で呼んでほしい」というデータを返すだけ。実行するのは自分のコード。server tools だけが例外で、実行が Anthropic 側で完結する。

会話の履歴は API 側が覚えているので、増分だけ送ればよい？

誤り。ステートレスなので毎回すべて送る。だからトークンが周回ごとに増える。

サブエージェントは親の会話履歴を自動で引き継ぐ？

誤り。必要な情報は明示的に渡す（explicit context passing）。引き継がないからこそ文脈を分離できる。

bash ツールは Anthropic 定義なので、実行もサーバー側で行われる？

誤り。定義は Anthropic、実行は自分のコード（client tool）。サーバー側で実行されるのは web_search などの server tools。

MAX_TURNS のような上限がなくても、end_turn が来れば必ず止まる？

危険。ツール結果を見て再びツールを呼び続ける状況では終わらない。ターン上限は必ず置く。
