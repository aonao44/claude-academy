01JSON必須

Claude とのやりとりは全部 JSON。読めればいい。書き方の規則は3つだけ。

{ } オブジェクト … 名前で引く

{
  "stop_reason": "tool_use",
  "role": "assistant"
}

「キー: 値」の集まり。順番に意味はなく、名前で取り出す。

[ ] 配列 … 順番に並ぶ

[
  {"type": "text", …},
  {"type": "tool_use", …}
]

同じ種類のものが0個以上並ぶ。1個とは限らないのが要点。

値の型

型書き方API での例
文字列"tool_use"（必ず二重引用符）stop_reason の値
数値700（引用符なし）max_tokens
真偽値true / false（小文字）is_error
nullnullstop_details（拒否以外のとき）
入れ子{ } や [ ] の中にまた { }content の中の各ブロック

引用符の有無は意味が違う。"700"（文字列）と 700（数値）は別物。"true" と true も別物。API がエラーを返す典型。

実物で見る → 04 やりとり再生 の右パネル。送った JSON と返ってきた JSON がそのまま出ている。

02「配列」と「単一の値」の区別必須

試験でもっとも効く区別。1つしか入らない場所と、複数入る場所がある。

フィールド形中身コードの書き方
stop_reason単一の文字列6つの候補から1つだけif res.stop_reason == "tool_use":
content配列ブロックが1個以上for b in res.content:
messages配列会話の全履歴messages.append(...)
tools配列ツール定義が複数—
inputオブジェクト引数名と値の組f(**b.input)

Python との対応。JSON の { } は Python の dict、[ ] は list。SDK が自動で変換してくれるので、手で直す必要はない。

03HTTP の基本必須

API を呼ぶとは、リクエストを送ってレスポンスを受け取ること。1往復で完結し、サーバーは次の呼び出しまで何も覚えていない。

ステータスコード

コード意味この API での例コードの扱い
200成功応答が返ってきた（stop_reason 入り）戻り値を見て分岐
400こちらの送り方が悪い履歴が長すぎる、引数の型が違う例外として飛んでくる
（try / except）
401認証エラーAPI キーが違う・未設定
429制限に達したレート制限・残高不足
500 系サーバー側の問題一時的な障害

ここが混ざりやすい。stop_reason は「応答が返ってきたときに、なぜ生成が止まったか」。応答そのものが作れなかった場合（400 など）は、stop_reason ではなくエラーになる。
出力が上限で切れた → stop_reason: "max_tokens"（200・正常レスポンス）／ 入力が長すぎた → 400 エラー。

04Python で使う分だけ必須

dict（辞書）… 名前で引く

out = {"verified": True, "customer_id": "C-2044"}
out["customer_id"]        # 無いとエラー
out.get("verified")        # 無ければ None

list（配列）… 順に回す

results = []
for b in res.content:
    results.append(...)

** で辞書を引数に展開

b.input = {"email": "a@b.com"}
f(**b.input)        # f(email="a@b.com") と同じ

Claude が返した引数を、そのまま関数に渡す仕掛け。input_schema の引数名と関数の引数名を揃える理由。

辞書で関数を引く

IMPL = {"get_customer": get_customer, …}
IMPL[b.name](**b.input)

Python では関数も値。名前（文字列）から関数を取り出せる。

try / except … 例外を受け止める

try:
    res = client.messages.create(...)
except anthropic.BadRequestError:
    ...   # 400 のとき

JSON 文字列との変換

json.dumps(out, ensure_ascii=False)   # dict → 文字列
json.loads(s)                           # 文字列 → dict

tool_result の content は文字列なので、dict は変換して入れる。

05ステートレス必須

API は前回のやりとりを覚えていない。だから毎回、最初からの履歴を全部送り直す。エージェントの挙動の多くがここから来る。

ここから派生する論点。プロンプトキャッシュ（同じ前置きを再利用して安くする）、コンテキスト編集（古い結果を消す）、圧縮（要約する）。いずれも「毎回全部送る」という性質への対処。

06JSON Schema加点

ツールの引数の形を書くための記法。覚えるのは4語だけで足りる。

"input_schema": {
  "type": "object",                          # 引数はいつもオブジェクト
  "properties": {                             # 引数の一覧
    "order_id": {"type": "string", "description": "注文番号"},
    "reason":   {"type": "string", "enum": ["返品", "不良"]}   # 選択肢を固定
  },
  "required": ["order_id"]                   # 必須の引数
}
語意味効き目
type値の種類（string / integer / boolean / object / array）型違いを防ぐ
properties引数名とその定義引数の一覧になる
required必須の引数省略を防ぐ
enum取りうる値を列挙選択肢を狭めて事故を減らす

試験での効き方。「余計な引数を消す」「enum で候補を絞る」は、プロンプトより確実な対策として選択肢に出る。構造で選べなくするのが強い、という発想。

07トークンと上限加点

トークンは文章を区切った単位（日本語ならおおよそ1〜2文字で1トークン）。課金も上限もこの単位。

用語何の上限か超えると
max_tokens出力の上限（自分で指定）stop_reason: "max_tokens"（正常レスポンス）
コンテキストウィンドウ入力＋出力の上限（モデルごとに固定）400 エラー

usage で実際の消費が見える。input_tokens（送った分）/ output_tokens（返ってきた分）/ cache_read_input_tokens（キャッシュから読めた分）。

08SDK とは加点

API を言語から呼びやすくしたライブラリ。中身の API は同じもので、SDK は包み紙にすぎない。

09覚えておくと読める用語加点

用語意味この文脈での例
enum（列挙）取りうる値が決まっているものstop_reason は6値の enum
スキーマデータの形の定義input_schema、DB のテーブル定義
ペイロード実際に送る中身のデータリクエストの JSON 本体
副作用外の世界を変えてしまう処理返金、削除、メール送信
冪等（べきとう）何度実行しても結果が同じ検索は冪等、返金は非冪等
決定論的必ず同じ結果になるコードによる条件チェック
確率的結果がばらつくプロンプトでの指示、Few-shot
境界責任や所有の切れ目API の境界、プロセスの境界
ステートレス / ステートフル状態を持たない / 持つMessages API は前者
エスカレーション人間に引き継ぐことescalate_to_human

副作用と冪等性がなぜ効くか。検索は間違えてもやり直せるが、返金は取り返せない。非冪等で副作用のある処理ほど、確率的な仕組みに任せてはいけないので、コードで止める（選択肢 A）という結論になる。
